```yaml
المهمة: إعداد V013 Migration Script

  1. مراجعة الهيكلية الحالية:
     - فحص visits table
     - فحص claims table
     - فحص eligibility_checks table
     - فحص pre_approvals table
  
  2. كتابة Migration Script:
     الملف: V013__unified_visit_workflow.sql
     
     المحتويات:
       - ALTER TABLE claims ADD COLUMN visit_id
       - ALTER TABLE eligibility_checks ADD COLUMN visit_id
       - CREATE INDEX idx_claims_visit_id
       - CREATE INDEX idx_eligibility_visit_id
       - Foreign Key Constraints
  
  3. كتابة Rollback Script:
     الملف: V013__unified_visit_workflow_rollback.sql

المخرجات:
  ✅ V013 migration script جاهز للاختبار
  ✅ Rollback plan موثق
```

**الملف المتوقع:**
```sql
-- V013__unified_visit_workflow.sql
-- ================================================
-- PURPOSE: Link all medical operations to unified visit_id
-- ================================================

-- 1. Add visit_id to claims table
ALTER TABLE claims 
  ADD COLUMN IF NOT EXISTS visit_id BIGINT;

ALTER TABLE claims 
  ADD CONSTRAINT fk_claims_visit 
  FOREIGN KEY (visit_id) 
  REFERENCES visits(id) 
  ON DELETE SET NULL;

CREATE INDEX IF NOT EXISTS idx_claims_visit_id 
  ON claims(visit_id);

-- 2. Add visit_id to eligibility_checks table
ALTER TABLE eligibility_checks 
  ADD COLUMN IF NOT EXISTS visit_id BIGINT;

ALTER TABLE eligibility_checks 
  ADD CONSTRAINT fk_eligibility_visit 
  FOREIGN KEY (visit_id) 
  REFERENCES visits(id) 
  ON DELETE SET NULL;

CREATE INDEX IF NOT EXISTS idx_eligibility_visit_id 
  ON eligibility_checks(visit_id);

-- 3. Comments for documentation
COMMENT ON COLUMN claims.visit_id IS 
  'Links claim to the originating medical visit';
  
COMMENT ON COLUMN eligibility_checks.visit_id IS 
  'Links eligibility check to a visit (optional - for post-check scenarios)';
```

### Sprint 2.1: Unified Visit Workflow (أسابيع 3-4)

#### Week 3: Backend Workflow Service
```yaml
المهمة: تطوير VisitWorkflowService
المسؤول: 2 Backend Developers

الملف الجديد:
  backend/.../visit/service/VisitWorkflowService.java

Methods:
  1. createUnifiedVisit(UnifiedVisitRequestDto):
     Steps:
       a. Check eligibility (via EligibilityEngineService)
       b. If eligible → create Visit
       c. Link eligibility check to visit
       d. Check if services need pre-approval
       e. Create pre-approval requests if needed
       f. Return UnifiedVisitResponseDto
  
  2. completeVisit(Long visitId, VisitCompletionDto):
     Steps:
       a. Update visit with actual services performed
       b. Create claim linked to visit
       c. Link pre-approvals to claim
       d. Submit to review workflow

DTOs:
  UnifiedVisitRequestDto:
    - memberId
    - serviceDate
    - providerId
    - services: List<ServiceRequestDto>
    - checkEligibility: boolean (default: true)
  
  UnifiedVisitResponseDto:
    - visitId
    - eligibilityStatus: ELIGIBLE | INELIGIBLE
    - eligibilityReasons: List<String>
    - preApprovalsNeeded: List<PreApprovalDto>
    - warnings: List<String>

المخرجات:
  ✅ Workflow service implemented
  ✅ Transaction management correct
  ✅ Error handling comprehensive
```

## 🔄 User Flows {#flows}

### Flow 1: التدفق الكامل من الأهلية إلى المطالبة

```
1. التحقق من الأهلية
   ├─ إدخال رقم البطاقة
   ├─ الضغط على "تحقق"
   └─ عرض النتيجة
       ├─ ✅ مؤهل → [2]
       └─ ❌ غير مؤهل → عرض الأسباب + إنهاء

2. تسجيل الزيارة (Wizard)
   ├─ Step 1: معلومات المريض (محملة)
   ├─ Step 2: تفاصيل الزيارة
   ├─ Step 3: الخدمات والتشخيص
   │   └─ فحص: هل تحتاج موافقة؟
   │       ├─ نعم → [3]
   │       └─ لا → [4]
   └─ Step 4: المراجعة والحفظ

3. طلب الموافقة المسبقة
   ├─ إنشاء طلب موافقة
   ├─ إرفاق المستندات
   ├─ إرسال للمراجع الطبي
   └─ انتظار القرار
       ├─ ✅ موافق → [4]
       └─ ❌ مرفوض → إخطار المريض + إنهاء

4. تنفيذ الخدمة
   └─ بعد تقديم الخدمة → [5]

5. إنشاء المطالبة
   ├─ ربط بـ Visit ID
   ├─ ربط بـ Pre-Approval ID (إن وجد)
   ├─ إدخال التفاصيل المالية
   └─ إرسال للمراجعة

6. مراجعة المطالبة
   └─ الموافقة/الرفض/التسوية
```

### 1.2 تقييم إمكانية الربط برقم زيارة موحد (Unified Visit ID)

#### ✅ **الإجابة: نعم - قابل للتنفيذ تقنياً**

**الأسباب:**

1. **جدول `visits` موجود ويحتوي على:**
   - معرف فريد (`id`)
   - علاقة بالعضو (`member_id`)
   - علاقة بالمنظمة (`employer_org_id`)
   - تاريخ الزيارة (`visit_date`)

2. **العلاقات الموجودة حالياً:**
   ```sql
   pre_approvals.visit_id → visits.id (موجود لكن اختياري)
   ```

3. **العلاقات المفقودة (تحتاج إضافة):**
   ```sql
   claims.visit_id → visits.id (غير موجود - يحتاج إنشاء)
   eligibility_checks.visit_id → visits.id (غير موجود - يحتاج إنشاء)
   ```

#### 🔨 **التعديلات المطلوبة على قاعدة البيانات:**

**Migration جديدة (V013):**
```sql
-- إضافة visit_id إلى جدول claims
ALTER TABLE claims 
  ADD COLUMN IF NOT EXISTS visit_id BIGINT REFERENCES visits(id);

CREATE INDEX IF NOT EXISTS idx_claims_visit_id ON claims(visit_id);

-- إضافة visit_id إلى جدول eligibility_checks
ALTER TABLE eligibility_checks 
  ADD COLUMN IF NOT EXISTS visit_id BIGINT REFERENCES visits(id);

CREATE INDEX IF NOT EXISTS idx_eligibility_visit_id ON eligibility_checks(visit_id);

-- جعل visit_id إلزامي في pre_approvals (بعد تعبئة البيانات الموجودة)
-- ALTER TABLE pre_approvals ALTER COLUMN visit_id SET NOT NULL; -- مرحلة لاحقة
```

**التكلفة الزمنية:** 1-2 يوم عمل (migration + testing)

## 📐 الجزء الثاني: سير العمل المقترح الجديد

### 2.1 التدفق الموحد المقترح (Unified Workflow)

```mermaid
graph TD
    A[استقبال المريض] --> B{التحقق من الأهلية}
    B -->|مؤهل| C[تسجيل الزيارة]
    B -->|غير مؤهل| X[رفض + إخطار]
    
    C --> D[إدخال الإجراءات الطبية]
    D --> E{هل تحتاج موافقة مسبقة؟}
    
    E -->|نعم| F[طلب الموافقة المسبقة]
    F --> G{حالة الموافقة}
    G -->|موافق| H[تنفيذ الخدمة]
    G -->|مرفوض| Y[رفض الخدمة]
    
    E -->|لا| H
    
    H --> I[إنشاء المطالبة]
    I --> J[مراجعة المطالبة]
    J --> K[الدفع/التسوية]
```

### 2.2 الربط بين الجداول (Unified Visit ID Design)

#### **العلاقات المقترحة:**

```sql
-- كل عملية مرتبطة بـ visit_id واحد
visits
  ├─→ eligibility_checks.visit_id (1:many) -- كل زيارة قد يكون لها عدة فحوصات
  ├─→ pre_approvals.visit_id (1:many)      -- زيارة واحدة قد تحتاج عدة موافقات
  └─→ claims.visit_id (1:1 or 1:many)      -- زيارة → مطالبة واحدة (أو أكثر)
```

#### **قواعد العمل المقترحة:**

1. **التحقق من الأهلية:**
   - يحدث **قبل** تسجيل الزيارة
   - أو يمكن ربطه بزيارة موجودة (حالة Post-check)

2. **الموافقات المسبقة:**
   - **يجب** أن تكون مرتبطة بـ `visit_id`
